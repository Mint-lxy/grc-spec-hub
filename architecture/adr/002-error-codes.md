# ADR-002: 统一错误码与错误响应规范

> 状态：Proposed
> 日期：2026-08-13 · 决策者：@todo-owner · 关联 spec：`specs/000-platform`（AC-G1 跨服务契约）

## 背景

平台由 8 个独立部署的服务组成（ADR-001），前端需要统一处理来自不同服务的错误。PRD 中定义了多种面向用户的错误提示（对话工作台四类文案、订阅被拒理由、护栏命中类型等），如果各服务自行定义错误格式，前端将无法统一展示，跨服务链路追踪也会断裂。

需要解决的问题：
1. 错误响应 JSON 结构不统一——前端无法通用解析
2. 错误码无命名空间——多服务同码冲突
3. 网关透传 vs 包装边界不清——前端不知道错误来自哪一层
4. 幂等与重试无统一约定——各服务实现不一致

## 决策

采用**全平台统一的错误码编码体系**，规范落地在 `architecture/cross-cutting/error-codes.md`。

核心决策点：

| # | 决策 | 理由 |
|---|------|------|
| 1 | 错误响应格式基于 RFC 9457 Problem Details，固定 6 字段（code/message/detail/traceId/timestamp/path） | 业界标准，OpenAPI 生态友好 |
| 2 | 错误码格式 `{SERVICE_PREFIX}-{CATEGORY}{SEQUENCE}`（如 `ASSET-3002`） | 前缀避免跨服务冲突，类别码可供前端按规则分级处理 |
| 3 | 服务前缀按 mgmt-service 内部模块粒度注册（15 个），而非按部署单元（8 个） | mgmt 内模块未来可能拆分，提前隔离码段避免迁移 |
| 4 | 网关对后端标准错误原样透传，对非标准错误包装为 `GW-9002` | 前端始终拿到统一结构 |
| 5 | 护栏拦截错误由网关自己生成（`GW-4001`/`GW-4002`），不透传后端 | 护栏执行在网关层，后端不感知 |
| 6 | 幂等键放 HTTP Header `X-Idempotency-Key` | 不污染 body schema；对 GET 无侵入 |
| 7 | 事件消费者以 `message_id` 去重 | Service Bus 至少一次投递语义 |
| 8 | 重试/超时按场景分 6 档，默认值对齐 PRD §9.10 | 平台参数基线 |

## 备选方案

| 方案 | 优点 | 缺点 | 为何不选 |
|------|------|------|----------|
| 仅用 HTTP 状态码，不自定义错误码 | 简单 | 同一 422 无法区分"门控未过"与"冗余不满足"；前端无法精准匹配 PRD 要求的四类文案 | 业务语义不够 |
| 错误码按部署单元注册（8 个前缀） | 前缀少 | mgmt-service 一个前缀下塞 7 个模块数百错误码，未来拆分需全量改码 | 扩展性差 |
| 幂等键放 body | 对 GraphQL 友好 | 侵入 schema，PUT/PATCH body 已有语义 | REST 不适合 |
| 全局统一超时（如全部 30s） | 配置简单 | 测评/构建分钟级任务会超时，资产调用 Owner 可配 5–120s | 不符合实际 |

## 影响

- 受影响服务：**全部**——所有服务的 REST 接口必须返回统一错误格式
- 契约影响：各服务 OpenAPI 的 error response schema 必须引用 `contracts/shared/error.schema.json`
- 前端影响：需实现统一错误拦截器，按类别码分级处理

## 后果

- 新增接口时必须在 `error-codes.md` 的示例表注册新错误码（人审 PR）。
- 网关需实现错误格式检测与包装逻辑。
- 各服务需引入统一的 error response 生成库（Java 侧建议 Spring `@ControllerAdvice`；Python 侧建议 FastAPI exception handler）。
