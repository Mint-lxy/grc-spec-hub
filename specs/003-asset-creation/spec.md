# Feature Specification: 资产创建与质量门控（高代码 Agent 与 MCP 创建向导）

**Feature Branch**: `spec-sync-prd-v1.2`（本文件为既有 AC 格式 spec 的 spec-kit 风格重写，对齐 PRD v1.2 全量口径；原 AC 编号对照见文末附录）

**Created**: 2026-08-13（初版，随 specs/001–009 拆解）；2026-08-21（v1.2 同步）；2026-08-23（spec-kit 风格重写 + 三轮澄清 + Zeng Ziyang peer review + 用户终审通过）

**Status**: Reviewed

**PRD 来源（v1.2）**: §7 M3（功能清单）、§6 J2.1–J2.3/J8（用户旅程）、§8.3 US39–US51/US60/US61、§9.1.1/§9.1.2/§9.3、§9.10、§11、§12.1/§12.4

**Input**: 自助式资产创建：高代码 Agent 六步向导与 MCP 五步向导（按资产类型参数化）、质量门控硬阻断（Agent 六项 / MCP 五项）、订阅配置（YAML 表单 / 独立使用条款 / 并行多级审批人链）、鉴权元数据声明、护栏策略模板必选。全员默认可创建资产，不设资格前置审批；质量由质量门控与发布准入测评（spec 004）把关。

---

## 背景与目标

提供资产的自助式创建入口：任何用户（全员默认，不设资格前置审批）可作为 Provider 经创作者中心创建高代码 Agent 或 MCP 资产。首次发布前不存在 Owner、Deputy 或负责人关系；首次发布成功后，系统才将 Provider 设为资产首位 Owner（见 spec 004）。创建向导产出资产的完整治理配置（接入、鉴权元数据、能力声明、订阅配置、护栏绑定），提交后进入质量门控硬阻断；门控全部通过后进入发布链路（状态机流转、准入测评与上架见 spec 004）。核心治理语义：Provider 只声明调用所需的凭据元数据，MUST NOT 配置、保存或访问密钥值；Consumer 在个人密钥库配置并实际验证自己的凭据。首发门控只校验凭据元数据完整合法，不依赖任何密钥值或真实鉴权。能力声明是上架时点契约记录、无运行时白名单效力。审批链的运行时推进语义（并行多级、死锁回落、在途快照、禁止自审）定义处在 spec 002（PRD §9.2），本 spec 只定义配置侧；护栏模板的维护与运行时语义在 spec 006；个人凭据与解析规则在 spec 007。

## Clarifications

### Session 2026-08-23

- Q: 创建向导草稿的持久化与协作可见性？ → A: 服务端持久化；首次发布前仅创建该资产的 Provider 可见并可继续编辑，不存在共同 Owner/Deputy。草稿即资产的一种状态，随资产生命周期存在，不设独立留存期限（后续 Provider→Owner 生命周期裁定取代原协作式草稿口径）。
- Q: Health Check 开关关闭时门控项②如何判定？ → A: **消除开关**——Health Check 为强制必选，首发前 Provider、发布后 Owner/Deputy 均不可关闭；接入配置不再提供开关，门控项②「Health Check 探测成功」因此无豁免路径（保障「门控保可用性、平台内调用开箱可调」承诺不被击穿）。注：该裁定超出 PRD 现表述（J2-2/M3-1 原文为「Health Check 开关与一键探测」），建议随业务规则补遗回写 PRD 与 spec 004 FR-016 版本类字段表述（用户裁定）。**注：2026-08-23 BA Lead（Zeng Ziyang）peer review 曾对本裁定暂缓确认（watchlist #56）；同日用户终审驳回暂缓、维持强制必选并关闭 #56**——补充理由：HC 若设开关被关闭，资产失效无法触达时订阅者与平台将无从知晓实际服务健康状态。PRD 强制表述维持，无需回滚。
- Q: 能力声明与 Agent Card / 工具清单拉取结果的关系——允许维护者手工编辑吗？ → A: **只读镜像**——声明内容完全以拉取结果为准，首发前 Provider、发布后 Owner/Deputy 均不可编辑；要变更只能修改服务后重新拉取（声明的全部价值是「上架时点的客观契约记录」供订阅者评估——既然无运行时白名单效力（`docs/adr/0011`），允许手工编辑会让记录既可漂移又看似权威；收窄暴露面应在服务端实现）（用户裁定）。
- Q: MCP「托管方式」的枚举集合？ → A: P0 单值「**远程服务（业务方自托管）**」——MCP 与 Agent 一致，平台在 P0 不提供托管服务，仅支持外部服务接入、由业务方自托管（与平台定位一致：资产安全与质量归业务方自负，`docs/adr/0004`）；字段保持枚举结构，为未来引入平台托管形态预留扩展（用户裁定）。
- Q: 首发质量门控如何校验凭据配置？ → A: **仅校验凭据元数据完整合法；Consumer 配置时再真实鉴权**。Provider 不提供密钥值，首发门控不得依赖秘密或执行真实鉴权；资产发布后，Consumer 在个人密钥库配置自己的凭据时执行真实鉴权，验证失败则该凭据不可用于调用（2026-08-23 用户选择 A；取代原动态凭据由 Provider 一键测试的裁定）。
- Q: MCP 链接配置的「协议」字段枚举？ → A: P0 单值「**Streamable HTTP**」，不兼容旧版 SSE；字段保持枚举结构，为未来协议扩展预留（MCP 现行标准的远程传输，2026-08-23 用户选择 A，取代此前待技术审核状态）。
- Q: 向导末步的「发布说明」合批位置是否统一？ → A: **维持现状并在文档明示**——统一规则为「向导末步＝该资产类型的最后一个治理配置＋发布说明」：Agent 末步＝护栏策略模板＋发布说明，MCP 末步＝订阅配置＋发布说明（MCP 无护栏步）；两类资产步骤数不同（六/五）系治理项差异的自然结果，内容物完全一致——不为形式对称制造近空步骤（用户裁定，要求文档明示防开发误读）。
- Q: 固定/单值字段在向导中的呈现方式？ → A: **只读展示**——Agent 接入配置显示「协议：A2A」，MCP 链接配置显示「协议：Streamable HTTP」「托管方式：远程服务（业务方自托管）」；字段对 Provider 是接入要求明示（决定其服务如何暴露），只读呈现统一两类资产的心智模型并为多值扩展预留位置（PRD v0.9 移除的是纯展示步骤，字段级协议明示不在其列——用户裁定）。
- Q: MCP 链接配置是否补齐 Health Check 探测与超时/重试（对齐 Agent 接入配置）？ → A: **全量补齐**——MCP 链接配置增加 Health Check（强制必选，与消除开关裁定一致）与一键探测、超时（默认 30 秒，可配范围 5 至 120 秒）与重试（默认 1 次，可配范围 0 至 3 次）；补齐后两类资产的接入配置字段集完全同构（此前门控项②对 MCP 生效却无配置入口，属真实断层；超时/重试是 §9.10 资产级通用参数——用户裁定）。
- Q: 资产名称的唯一占用从哪个时点生效？ → A: **提交门控时才校验**——草稿可同名并存（草稿是半成品，落库即占用会造成名称囤积）；唯一约束覆盖「待发布/待测评/已发布/已下架」，不含草稿、不含已删除（已删除名称已释放）；两个同名草稿并存时先提交者占用、后提交者被门控阻断（与「门控是上架前唯一防线」定位自洽——用户裁定）。
- Q: Agent Card / MCP 工具清单拉取失败时如何重试？ → A: **不自动重试，仅允许 Provider 手动重试**。失败时立即展示可诊断的错误原因并保持对应门控项不通过，避免配置错误或服务持续不可达时产生隐藏等待（2026-08-23 用户选择 C）。
- Q（跨 spec 裁定，源自 spec 004 澄清会话）: Provider 与 Consumer 分别负责哪些凭据内容？ → A: **Provider 仅声明凭据元数据，Consumer 在个人密钥库配置密钥值**。Provider 不得配置、保存、发布或读取 Consumer 密钥值；凭据变量名变化走版本发布，生效后使相关 Consumer 个人凭据失效并通知其重新配置（2026-08-23 后续用户裁定，取代原“资产级服务凭据密钥值轻发布”口径）。

## User Scenarios & Testing

### User Story 1 — Provider 创建高代码 Agent（六步向导） (Priority: P1)

用户在创作者中心点击「创建 Agent」选择高代码方式（前置条件：该 Agent 服务已对外暴露符合 A2A 协议的 Agent Card），依次完成六步向导：基础信息 → 接入配置 → 鉴权配置 → 能力声明 → 订阅配置 → 护栏策略模板与发布说明；提交后系统运行质量门控。

**Why this priority**: 高代码 Agent 是平台最主要的资产类型，该向导是资产进入治理体系的唯一入口，无此则平台无任何资产。

**Independent Test**: 以一个有真实 Agent Card 的服务走完整六步并提交，验证各步字段、校验（名称唯一、YAML 表单、凭据元数据 schema）与门控触发；全程不填写或读取密钥值，故意制造门控失败项验证阻断与原因展示。

**Acceptance Scenarios**:

1. **Given** 任意已登录用户（无需任何资格审批）, **When** 进入创作者中心创建高代码 Agent, **Then** 创建入口可用，创建者成为该资产的 Provider；首次发布成功前不创建 Owner/Deputy 关系。
2. **Given** 基础信息步, **When** Provider 填写资产名称, **Then** 名称在草稿阶段可与他人草稿同名（不占唯一约束），提交时校验全平台唯一（重名阻断并提示；已删除资产的名称已释放可用）；页面不提供 Owner、Deputy 或负责人配置。
3. **Given** 接入配置步, **When** 填写服务地址与运行参数, **Then** 页面只读展示「协议：A2A」；Health Check 强制必选（无开关）且可一键探测；可配置超时（默认 30 秒，可配范围 5 至 120 秒）与重试（默认 1 次，可配范围 0 至 3 次）。
4. **Given** 鉴权配置步, **When** Provider 声明鉴权模式, **Then** 静态凭据模式声明鉴权方式、变量名、注入位置与必填性；动态凭据模式另声明授权申请接口地址与令牌回写字段；页面不提供密钥值输入或真实鉴权测试，保存与门控只校验元数据 schema。
5. **Given** 能力声明步, **When** 拉取 Agent Card, **Then** 拉取成功则以拉取结果声明输入输出结构（只读镜像，Provider 不可编辑）；拉取失败或格式不合法时给出明确错误，且该状态在质量门控中不通过。
6. **Given** 订阅配置步, **When** 定义订阅申请表单, **Then** 支持下载 YAML 模板、上传、在线编辑与实时预览；保存时强制通过格式与 schema 校验，不合规定义不允许保存（问题不流到订阅者侧）；使用条款为独立必填文本、与表单分开维护、自带版本号。
7. **Given** 订阅配置步的审批人链区域, **When** 配置审批链, **Then** 可视化配置并行多级（可增删审批级、每级可设多个审批人；上限 3 级、每级至多 10 人）；可整体关闭审批。
8. **Given** 末步, **When** 选择护栏策略模板并填写发布说明, **Then** 必须从启用状态的模板中选择恰好一个（选择前可只读查看模板条目明细——护栏、灵敏度、作用侧，选择不是盲选）；发布说明随本次首发写入发布记录。
9. **Given** 向导提交, **When** 系统运行质量门控, **Then** 执行 Agent 六项检查并逐项展示判定结果；全部通过方可进入发布链路下一步（待测评），任一项未通过则阻断。

### User Story 2 — Provider 创建 MCP 资产（五步向导） (Priority: P1)

用户创建 MCP 资产，五步向导：基础信息 → 链接配置（服务地址、协议与托管方式）→ 鉴权配置（静态凭据与动态凭据）→ 能力声明（拉取工具清单）→ 订阅配置与发布说明；提交后运行 MCP 五项质量门控。

**Why this priority**: MCP 是两类资产之一，与 Agent 共享同一治理流程（同一门控引擎、参数化检查项），是 Marketplace 完整性的必要半边。

**Independent Test**: 以一个 MCP 服务走完五步并提交，验证链接配置（含托管方式）、工具清单拉取与五项门控；验证 MCP 向导不出现护栏模板选择或密钥值输入。

**Acceptance Scenarios**:

1. **Given** 创建 MCP 资产, **When** 进入链接配置步, **Then** 填写服务地址，协议与托管方式为只读展示的单值字段（「Streamable HTTP」/「远程服务（业务方自托管）」，均为版本类字段），并配置 Health Check（强制必选）与一键探测、超时（默认 30 秒，5 至 120 秒）与重试（默认 1 次，0 至 3 次）——与 Agent 接入配置字段集同构。
2. **Given** 鉴权配置步, **When** Provider 声明鉴权, **Then** 支持静态凭据与动态凭据两种模式，口径与 Agent 向导一致，仅配置凭据元数据，不配置或测试密钥值。
3. **Given** 能力声明步, **When** 拉取工具清单, **Then** 拉取成功则以拉取结果声明工具清单（只读镜像，Provider 不可编辑）；拉取失败或格式不合法给出明确错误并在门控中不通过。
4. **Given** 末步（订阅配置与发布说明）, **When** 完成配置, **Then** 订阅配置含申请表单、使用条款与审批配置，语义与 Agent 向导一致；**不出现护栏策略模板选择**——外部接入的 MCP 不单独绑定护栏，其返回内容进入对话上下文后由输出侧护栏检测覆盖（spec 006）。
5. **Given** 向导提交, **When** 系统运行质量门控, **Then** 执行 MCP 五项检查（不含护栏模板项）；全部通过后 MCP 直接转「已发布」上架并将 Provider 设为首位 Owner（MCP 免跑准入测评，见 spec 004）。

### User Story 3 — 质量门控硬阻断与重跑 (Priority: P1)

质量门控按资产类型参数化、硬阻断：Agent 六项 / MCP 五项逐项判定，任一项未通过则阻断进入发布下一步；Provider 可清楚看到每一项的判定条件与未通过原因，修改后重新运行。

**Why this priority**: 门控是「不设资格前置审批」前提下的唯一质量防线，其硬阻断与可诊断性直接决定上架资产的基线质量。

**Independent Test**: 分别构造六项/五项中每一项的失败样本，验证阻断行为、原因展示与修改后重跑；验证凭据门控仅检查元数据 schema，不请求任何密钥值或执行真实鉴权。

**Acceptance Scenarios**:

1. **Given** Agent 资产提交, **When** 运行质量门控, **Then** 六项全部通过方可进入下一步：基础信息完整、Health Check 探测成功、Agent Card 可拉取且格式合法、凭据元数据完整且通过 schema 校验、订阅申请表单与使用条款已配置、所绑护栏策略模板当前处于启用状态。
2. **Given** MCP 资产提交, **When** 运行质量门控, **Then** 五项全部通过：基础信息完整、Health Check 探测成功、工具清单可拉取且格式合法、凭据元数据完整且通过 schema 校验、订阅配置已完成。
3. **Given** 任一门控项未通过, **When** 查看结果, **Then** 展示每一项的判定条件与未通过原因（便于定位修复）；资产停留「待发布」，修改后需重新运行门控。
4. **Given** 首次发布前运行质量门控, **When** 检查角色与凭据, **Then** 不校验 Owner/Deputy 或负责人冗余，不要求 Provider 提供密钥值，也不执行真实鉴权。
5. **Given** 资产已上架, **When** Owner 进行热改类变更或纯条款轻发布, **Then** 不触发门控重跑、不影响在架可见性——门控结果为上架时点快照；「任一配置字段变更后需重新运行」仅适用于发布流程与含版本类字段的未发布修订（spec 004）。

### User Story 4 — 鉴权元数据与 Consumer 个人凭据 (Priority: P2)

Provider 在向导鉴权配置步声明资产调用所需的凭据元数据，声明进入调用契约并属于版本类配置；Provider 不接触密钥值。资产发布后，每个 Consumer 在个人密钥库配置并真实验证自己的密钥值，平台调用时按当前 Consumer 解析其个人凭据。

**Why this priority**: 元数据与秘密分离可防止 Provider 获得 Consumer 凭据，并使每个 Consumer 独立轮换或撤销自己的秘密；变量名变化仍通过版本发布治理影响范围。

**Independent Test**: 分别以静态与动态模式提交合法和非法元数据，验证首发门控只做 schema 校验；发布后由 Consumer 配置个人凭据并执行真实鉴权，验证失败时凭据不可用于调用，且 Provider 始终无法读取密钥值。

**Acceptance Scenarios**:

1. **Given** 静态凭据模式, **When** Provider 配置, **Then** 仅声明鉴权方式、变量名、注入位置与必填性；页面不展示密钥值输入。
2. **Given** 动态凭据模式, **When** Provider 配置, **Then** 仅声明授权申请接口地址、令牌回写字段及所需凭据变量；页面不执行依赖密钥值的真实鉴权。
3. **Given** Provider 提交创建向导, **When** 质量门控检查鉴权配置, **Then** 只验证元数据字段完整性、枚举值和字段组合合法性，不读取密钥值、不调用授权接口。
4. **Given** 资产已发布且 Consumer 配置个人凭据, **When** 保存配置, **Then** 系统使用该 Consumer 的密钥值执行真实鉴权；成功后凭据方可用于调用，失败时显示明确错误且保持不可用。
5. **Given** Consumer 调用资产, **When** 平台解析凭据, **Then** 仅使用当前 Consumer 对该资产配置的个人凭据；Provider 不得读取、导出或修改该密钥值。
6. **Given** Owner 修改凭据变量名并成功发布新版本, **When** 新版本生效, **Then** 系统将相关 Consumer 的既有个人凭据标记为失效，并通知其重新配置（发布语义见 spec 004）。

### User Story 5 — 订阅审批人链配置 (Priority: P2)

Provider 在创建向导中可视化配置并行多级审批人链（各级同时收到待办、级间无顺序、每级至少一人通过），可整体关闭审批；上架后由 Owner/Deputy 在资产控制台调整，仅对新申请生效。

**Why this priority**: 审批链是订阅授权的把关结构；其配置侧属于创建向导，运行时推进语义属于 spec 002。列为 P2 是因为可用关闭审批或单级审批人配置跑通最小闭环。

**Independent Test**: 配置一条两级多人审批链并上架，验证仅对新申请生效的调整语义与关闭审批后的待办去向。

**Acceptance Scenarios**:

1. **Given** 审批人链配置, **When** 首发前 Provider 或发布后 Owner/Deputy 编辑, **Then** 可增删审批级、每级可设多个审批人；上限 3 级、每级至多 10 人；申请提交后各级同时收到待办、级间无先后依赖，每级至少一人通过即该级通过（运行时语义见 spec 002）。
2. **Given** 审批被关闭, **When** 订阅申请提交, **Then** 申请直接进入全体 Owner 与 Deputy 的待办队列，任一处理即可，不会自动通过。
3. **Given** 资产已上架, **When** Owner 或 Deputy 在资产控制台调整审批链, **Then** 调整仅对新申请生效——在途申请按提交时锁定的审批链快照走完（spec 002）。
4. **Given** 配置审批人链, **When** 指定审批人, **Then** 审批人可以不是资产负责人；平台管理员不参与常规订阅审批。

### Edge Cases

- 向导中途退出？——未提交的资产以「草稿」状态在服务端保留，仅创建该资产的 Provider 可再次进入续填（FR-004）。
- Agent Card / 工具清单拉取失败（服务不可达、超时、格式不合法）？——不自动重试，立即展示明确错误并使对应门控项不通过；Provider 修复问题后手动触发重试。
- Consumer 个人凭据真实鉴权失败？——显示明确错误，凭据保持不可用；不影响其他 Consumer，也不改变资产发布状态。
- Provider 提交的凭据元数据缺字段或字段组合非法？——门控项④不通过并逐项指出 schema 错误，不请求任何密钥值。
- 首次发布前是否可配置 Owner/Deputy？——不可；创建者保持 Provider 身份，首次发布成功时才转为首位 Owner（spec 004 FR-039）。
- 资产名称与现有资产（含「已下架」）重名？——提交（门控）或改名时阻断并提示名称已被占用；草稿可同名并存，先提交者占用；已删除资产的名称已释放（spec 004 FR-040，2026-08-23 用户裁定）。
- 审批链配置了某级但审批人全部失效（账号被 Alice 停用）？——不阻断创建与上架；运行时该级自动回落至任一 Owner 或 Deputy（spec 002 / PRD §9.2 死锁兜底）。
- 订阅表单 YAML 上传后在线编辑引入语法错误？——保存时强制校验拦截，不合规定义不允许保存（FR-017）。
- 服务实际能力与已上架的能力声明发生漂移？——声明为只读镜像：Owner 须修改服务后重新拉取，并经版本发布更新声明；平台不做指纹比对与持续校验，持续一致性责任归 Owner（FR-010、`docs/adr/0011`）。

## Requirements

### Functional Requirements

**创建入口与草稿**

- **FR-001**: 系统 MUST 允许全员默认以 Provider 身份创建 Agent 与 MCP 资产，MUST NOT 设资格前置审批；首次发布成功前 MUST NOT 创建 Owner、Deputy 或负责人关系，首次发布成功后由系统将 Provider 设为首位 Owner（spec 004 FR-039；后续用户裁定取代 PRD §9.1.2 原口径）。
- **FR-002**: 高代码 Agent 创建的前置条件 MUST 为：该 Agent 服务已对外暴露符合 A2A 协议的 Agent Card（PRD J2-1）。
- **FR-003**: 资产名称 MUST 全平台唯一——校验时点为**提交（门控）时**与基础信息热改（改名）时，重名阻断并提示；草稿可同名并存（不占用唯一约束），唯一约束覆盖「待发布/待测评/已发布/已下架」，已删除资产的名称已释放可用（spec 004 FR-040，2026-08-23 用户裁定；校验时点为同日裁定）。
- **FR-004**: 向导未提交的资产 MUST 处于「草稿」状态并在服务端持久化，仅创建该资产的 Provider 可见并可继续编辑；草稿即资产的一种状态，随资产生命周期存在，MUST NOT 设独立留存期限（状态机与可见范围定义处见 spec 004 FR-001/002）。

**高代码 Agent 创建向导（六步）**

- **FR-005**: Agent 创建向导 MUST 为六步：基础信息 → 接入配置 → 鉴权配置 → 能力声明 → 订阅配置 → 护栏策略模板与发布说明。步骤合批规则（两类资产统一，防误读）：**向导末步＝该资产类型的最后一个治理配置＋发布说明**——Agent 的末步治理项为护栏策略模板（原 AC-1；PRD M3-1、J2-2；合批规则明示为 2026-08-23 用户裁定）。
- **FR-006**: 基础信息 MUST 含：资产名称、业务标签、简介、能力标签、适用场景；首次发布前 MUST NOT 展示或维护 Owner、Deputy 或负责人名单（原 AC-2；角色生命周期见 FR-001/spec 004 FR-039）。
- **FR-007**: 接入配置 MUST 含：服务地址、Health Check（**强制必选，Provider 不可关闭**——不提供开关）与一键探测、超时（默认 30 秒，可配范围 5 至 120 秒）与重试（默认 1 次，可配范围 0 至 3 次）；并以只读方式展示「协议：A2A」作为接入要求明示（原 AC-3；PRD M3-1、§9.10；Health Check 强制化与协议只读展示为 2026-08-23 用户裁定——强制化经 peer review 暂缓后由用户终审维持成立，watchlist #56 关闭）。
- **FR-008**: 鉴权配置 MUST 支持两种元数据模式：静态凭据——声明鉴权方式（API Key、Bearer Token、OAuth2、自定义 Header）、变量名、注入位置与必填性；动态凭据——另声明授权申请接口地址、令牌回写字段及所需凭据变量。Provider 侧 MUST NOT 提供密钥值输入或执行依赖密钥值的真实鉴权；MUST NOT 要求声明鉴权主体类型（原 AC-4；2026-08-23 用户选择 A）。
- **FR-009**: Provider MUST 仅配置凭据元数据，MUST NOT 配置、保存、发布、读取或导出任何 Consumer 密钥值。首发质量门控 MUST 仅校验凭据元数据 schema 的完整性与合法性。资产发布后，Consumer MUST 在个人密钥库配置自己的密钥值，并在配置时执行真实鉴权；验证成功后方可用于调用（个人凭据存储与解析见 spec 007；版本变更影响见 spec 004 FR-017）。
- **FR-010**: 能力声明 MUST 拉取 Agent Card 并声明输入输出结构；声明内容 MUST 为拉取结果的**只读镜像**——首发前 Provider、发布后 Owner/Deputy 均不可编辑，要变更只能修改服务后重新拉取（重新拉取后的差异随版本发布生效，属版本类变更）；能力声明是上架时点的契约记录，MUST NOT 具有运行时白名单效力。拉取失败时 MUST NOT 自动重试，MUST 立即展示可诊断错误并仅允许维护者手动重试（原 AC-6；PRD M3-1、§9.1.1、`docs/adr/0011`；只读镜像语义与重试策略为 2026-08-23 用户裁定）。
- **FR-011**: 护栏策略模板 MUST 从启用状态的模板中选择恰好一个（不可不选、不可多选）；首发前 Provider、发布后 Owner/Deputy MUST 可只读查看启用模板的条目明细（护栏、灵敏度、作用侧）——选择不是盲选（原 AC-8；PRD M6-3、`docs/adr/0002`）。

**MCP 创建向导（五步）**

- **FR-012**: MCP 创建向导 MUST 为五步：基础信息 → 链接配置 → 鉴权配置 → 能力声明 → 订阅配置与发布说明（第五步分两个子区域：订阅配置含申请表单、使用条款与审批配置；发布说明填写本次发布说明）。步骤合批规则与 Agent 统一（FR-005）：末步＝最后一个治理配置＋发布说明——MCP 无护栏策略模板步，故末步治理项为订阅配置；两类资产内容物完全一致，步骤数差异（六/五）系治理项差异的自然结果，**不为形式对称制造近空步骤**（原 AC-9；PRD M3-2；合批规则明示为 2026-08-23 用户裁定）。
- **FR-013**: 链接配置 MUST 含：服务地址、协议、托管方式、Health Check（强制必选、不可关闭）与一键探测、超时（默认 30 秒，可配范围 5 至 120 秒）与重试（默认 1 次，可配范围 0 至 3 次）——与 Agent 接入配置（FR-007）字段集完全同构（2026-08-23 用户裁定，补齐门控项②的配置承载与 §9.10 通用参数的 MCP 侧入口）。协议与托管方式为版本类字段，上架后变更须经未发布修订（spec 004 FR-016）；托管方式 P0 仅「远程服务（业务方自托管）」、协议 P0 仅「Streamable HTTP」各一个取值，MUST NOT 支持旧版 SSE；两个单值字段 MUST 以只读方式展示（接入要求明示，不做可编辑单值下拉），均保持枚举结构为未来扩展预留（原 AC-10；PRD M3-2、§9.1.1；2026-08-23 用户选择 A）。
- **FR-014**: MCP 能力声明 MUST 拉取工具清单，且同样为拉取结果的**只读镜像**；拉取失败时不自动重试、立即展示可诊断错误并仅允许维护者手动重试（语义同 FR-010，2026-08-23 用户裁定）（原 AC-11；PRD M3-2）。
- **FR-015**: MCP 鉴权配置 MUST 支持静态凭据与动态凭据，口径与 Agent 向导一致（FR-008/FR-009 同样适用）（PRD M3-2）。
- **FR-016**: MCP 向导 MUST NOT 出现护栏策略模板选择——外部接入的 MCP 不单独绑定护栏，其返回内容进入对话上下文后由输出侧护栏检测覆盖（spec 006；PRD §9.5、M6）。

**订阅配置**

- **FR-017**: 订阅申请表单 MUST 支持下载 YAML 模板、上传表单定义文件、在线编辑与实时预览；保存（含上架后资产控制台热改通道）时 MUST 强制通过格式与 schema 校验，不合规定义不允许保存——问题不流到订阅者侧；表单属热改类，控制台即时生效（原 AC-16；PRD M3-5；spec 002 联动，2026-08-21 用户裁定）。
- **FR-018**: 使用条款 MUST 为资产的独立必填配置、与表单定义分开维护、自带版本号；条款变更走轻发布（通道语义定义处见 spec 004 FR-018；原 AC-17；PRD M3-6）。
- **FR-019**: 订阅审批人链 MUST 可视化配置为并行多级：可增删审批级、每级可设多个审批人；上限 3 级、每级至多 10 人；MUST 可整体关闭审批（关闭后订阅申请直接进入全体 Owner 与 Deputy 的待办队列，任一处理即可）；上架后可调整，仅对新申请生效（原 AC-18；PRD M3-7、§9.2、§9.10）。
- **FR-020**: 审批人可以不是资产负责人；平台管理员 MUST NOT 参与常规订阅审批（PRD M3-7、§9.2）。
- **FR-021**: 向导末步 MUST 填写本次发布说明，随首发写入发布记录（PRD M3-1/M3-2、J2-2）。

**质量门控**

- **FR-022**: 质量门控 MUST 按资产类型参数化、硬阻断。**Agent 六项**：①基础信息完整；②Health Check 探测成功；③Agent Card 可拉取且格式合法；④凭据元数据完整且通过 schema 校验；⑤订阅申请表单与使用条款已配置；⑥所绑护栏策略模板当前处于启用状态。**MCP 五项**：①基础信息完整；②Health Check 探测成功；③工具清单可拉取且格式合法；④凭据元数据完整且通过 schema 校验；⑤订阅配置已完成。门控 MUST NOT 请求密钥值或执行真实鉴权（原 AC-12/AC-13；2026-08-23 后续用户裁定取代 PRD M3-4 原凭据与负责人冗余口径）。
- **FR-023**: 首次发布门控 MUST NOT 校验 Owner、Deputy 或负责人冗余；首次发布成功后，系统按 spec 004 FR-039 将 Provider 设为首位 Owner。
- **FR-024**: 任一门控项未通过 MUST 阻断进入发布下一步，修改后需重新运行；每项 MUST 展示判定条件与未通过原因（原 AC-14；PRD M3-4、US-51）。
- **FR-025**: 门控结果 MUST 为上架时点快照：上架后的热改类配置变更与纯条款轻发布 MUST NOT 触发门控重跑、不影响在架可见性；「任一配置字段变更后需重新运行」仅适用于发布流程与含版本类字段的未发布修订（原 AC-15；PRD M3-4、§9.1.1）。
- **FR-026**: 门控全部通过 MUST 是状态机流转前提：Agent 转「待测评」进入准入测评，MCP 直接转「已发布」；任一类型首次发布成功时，系统将 Provider 设为首位 Owner（流转与测评语义定义处见 spec 004 FR-001/FR-005/FR-039）（PRD §9.1）。

### Key Entities

- **资产草稿（Asset Draft）**: 创建向导的未提交产物，服务端持久化。关键属性：类型（Agent/MCP）、名称（提交时校验全平台唯一，删除后释放）、基础信息五字段、Provider ID、向导各步完成度、状态（草稿/待发布）。仅 Provider 可见可续填；不设独立留存期限。
- **能力声明（Capability Declaration）**: 拉取结果的只读镜像（版本类）。关键属性：来源（Agent Card / 工具清单）、拉取时间、输入输出结构或工具清单内容；首发前 Provider、发布后 Owner/Deputy 均不可编辑，变更只能改服务后重新拉取并经版本发布生效。
- **鉴权声明（Auth Declaration）**: 资产接入的鉴权约定（版本类）。关键属性：鉴权模式（静态/动态）、鉴权方式与参数名、动态模式的授权申请接口地址与令牌回写字段。
- **凭据元数据（Credential Metadata）**: Provider 声明的资产调用契约。关键属性：模式（静态/动态）、鉴权方式、变量名、注入位置、必填性，以及动态模式的授权申请接口地址与令牌回写字段；不含任何密钥值。
- **Consumer 个人凭据（Consumer Personal Credential）**: Consumer 在个人密钥库中按“用户 + 资产”维护的秘密值；配置时执行真实鉴权，Provider 不可见。实体细节与生命周期见 spec 007。
- **订阅申请表单定义（Subscription Form Definition）**: YAML 格式的申请字段定义（热改类）。保存须经格式与 schema 校验；支持实时预览。
- **审批人链（Approval Chain）**: 并行多级结构（≤3 级、每级 ≤10 人），可整体关闭。运行时语义（级间并行、死锁回落、在途快照、禁止自审）见 spec 002。
- **质量门控结果（Gate Result）**: 一次门控运行的逐项判定快照。关键属性：检查项集合（按资产类型参数化）、逐项结果与失败原因、运行时间；为上架时点快照，热改不回溯。
- **使用条款**: 独立必填配置，自带版本号（实体定义见 spec 004）。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 任意用户（无预配角色）无需任何资格审批即可开始创建资产——创建入口 100% 可见可用。
- **SC-002**: 门控未全部通过的资产 100% 被阻断进入发布下一步；每一未通过项 100% 展示判定条件与失败原因。
- **SC-003**: 不合规的订阅表单 YAML 定义 0 次流入订阅者侧（保存即拦截率 100%）。

## Assumptions

- 质量门控执行与资产状态机流转由 mgmt-service 承载；Agent Card / 工具清单的拉取由对应服务经资产服务地址执行（architecture/service-map.md；错误码对齐 hub ADR-002）。
- 护栏策略模板由平台管理员维护（spec 006/008），平台默认模板随部署内置（PRD §12.3）；本 spec 只消费「启用模板集合」。
- 审批链的运行时推进语义（并行多级、死锁回落、在途申请快照、禁止自审）定义处在 spec 002（PRD §9.2）；本 spec 只定义配置侧与生效时机。
- Consumer 个人凭据底层加密存储走企业 Key Vault；凭据解析规则与真实鉴权流程见 spec 007。Provider 侧只存凭据元数据，不存密钥值。
- 发布准入测评、未发布修订、轻发布与版本发布链路见 spec 004；本 spec 只定义向导产物如何进入该链路。
- Consumer 配置静态或动态个人凭据时均执行真实鉴权；首发质量门控不执行该测试，也不因此依赖任何 Consumer。
- 质量门控对同一资产的运行串行、幂等——重复提交/重复触发不产生并行门控运行（与 spec 004 发布全互斥裁定同构；合理默认）。
- 草稿由单一 Provider 编辑；上架后资产控制台的并发编辑采用版本校验乐观锁（提交携带读取时版本，不匹配拒绝并提示刷新）。
- 审批人链配置时从 Alice 同步的用户中选择并校验账号存在性；审批人后续失效的兜底在运行时（死锁回落，spec 002 / PRD §9.2）。

## Non-Goals / Boundaries

- **低代码 Agent 创建**（P1）：Dify 实例与工作区选择、跳转编排或勾选已有 Agent 接入、元数据周期同步落入未发布修订（PRD J3、M3-8）。
- **平台托管运行资产**（P0 不承接）：MCP 与 Agent 均仅支持外部服务接入、由业务方自托管；MCP「托管方式」字段以枚举结构为未来托管形态预留扩展（2026-08-23 用户裁定）。
- **资格前置审批**：不设——全员默认可创建，质量由门控与准入测评把关（PRD §4）。
- **发布准入测评与发布链路**（含状态机流转、轻发布、上下架）：spec 004。
- **审批链运行时语义**（推进、驳回、回落、快照）：spec 002。
- **护栏模板维护与运行时命中处置**：spec 006；模板维护入口在管理后台（spec 008）。
- **Consumer 个人凭据与 PAT 管理**：spec 007；本 spec 只定义 Provider 侧凭据元数据及首发 schema 门控。
- **能力声明的运行时白名单**：不设——声明为上架时点契约记录，持续一致性责任归 Owner（PRD §12.4、`docs/adr/0011`）。
