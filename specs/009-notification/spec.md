# Feature Specification: 通知服务（站内通知轻量版）

**Feature Branch**: `spec-sync-prd-v1.2`（本文件为既有 AC 格式 spec 的 spec-kit 风格重写，对齐 PRD v1.2 全量口径并纳入 2026-08-23 spec 004 终审裁定的通知连带项；原 AC 编号对照见文末附录）

**Created**: 2026-08-13（初版，随 specs/001–009 拆解）；2026-08-21（v1.2 同步）；2026-08-23（spec-kit 风格重写 + 澄清会话，用户终审通过并授权直升 Reviewed）

**Status**: Reviewed

**PRD 来源（v1.2）**: §7 M9（功能清单）、§8.9 US140–US150、§5.1（P0 无通知中心一级入口）、§9.1/§9.2（下架与中止的通知触发点）、§9.8（通知留存）、§9.10（分页基线）、§12.1/§12.2

**Input**: 站内通知能力（P0 轻量版）：顶栏未读角标 + 通知列表，覆盖十三类关键业务事件（订阅申请与审批、测评完成、知识库构建、订阅取消、资产发布新版本、使用条款升版、资产下架、孤儿资产补员、出站调用停用与恢复、Health Check 连续失败、个人模型凭据回落、资产治理通知（负责人）），确保资产生命周期变更、订阅状态变化、安全事件等信息及时送达相关方。

---

## 背景与目标

提供平台的站内通知能力（P0 轻量版）：顶栏铃铛未读角标 + 通知列表，不提供分类筛选与跨模块深度跳转（P1 通知中心承载）。通知是平台「使用授权有留痕、相关方知情」承诺的最终触达点：订阅与审批、资产生命周期（发布/升版/下架/补员）、治理动作（出站停用）、长耗时任务结果（测评/构建）、凭据安全事件（个人模型凭据回落）均需按既定受众与附件口径送达。本 spec 定义事件触发条件、受众与附件口径；触发点语义（何时下架、何时版本替换等）的定义处在各源 spec（002/004/005/008 等），本 spec 只承载通知侧。

## Clarifications

### Session 2026-08-23

- Q: 密钥值轻发布的「密钥值」指什么，受众应为谁？ → A: 密钥值＝资产级服务凭据的密钥部分（平台→资产服务段的认证凭证：静态模式的固定密钥值 / 动态模式换取令牌的密钥），**订阅者从不接触它**。用户裁定：它是平台与资产的契约而非订阅者与资产的契约，原「通知存量订阅者与待审批申请人」口径属范畴错配——**收窄为仅通知全体负责人（Owner/Deputy）**，同步修正 spec 004 FR-018 与 PRD §9.1.1。
- Q: 「打开即置为已读」的粒度——打开单条还是打开列表？ → A: **逐条已读**——打开单条通知才将该条置为已读，角标未读数＝真实未读条数（通知承载治理与安全事件，「看过才算读」是知情留痕的最低诚信线）；**同时提供「全部设为已读」按钮**（用户裁定）。
- Q: 通知去重策略——短时间内同一事件多次触发，合并还是逐条？ → A: **不去重，逐条产生**——每条通知对应一次真实事件，可与发布记录等业务记录对照（通知是审计与知情的记录面，事件忠实优先）；刷屏风险集中于高频事件（如 Health Check 连续失败），由专项抑制策略处理而非全局合并窗口（用户裁定；关闭原 Open Question「去重策略」）。
- Q: Health Check 连续失败通知的抑制策略？ → A: **失败链抑制**——连续失败达阈值（3 次）通知一次，此后该失败链不再重复通知；探测成功一次即重置，新失败链重新计（无时间魔数、行为确定可测试；恢复后再次失败仍会重新通知，保留新故障感知）。抑制仅作用于通知通道——Marketplace 卡片「当前不可达」标记与详情页「运行状态」字段为实时探测结果的常显面，不受抑制影响（用户裁定；关闭原 Open Question「抑制间隔」）。
- Q: 三条裁定连带事件（中止发布/密钥值轻发布/发布失败）的归类（#54）？ → A: **合并为一类「资产治理通知（负责人）」**（十二类 → 十三类），受众统一为负责人侧，按载荷区分三种事件（中止发布＝修订保留事实，通知发起该次发布的 Owner/Deputy；凭据更新＝变更事实，不含密钥值，通知全体负责人；发布失败＝失败阶段与原因摘要，通知全体负责人）。P0 无分类筛选，合并成类不损失可用性且控制事件类型总量（用户裁定）；轻发布同时含条款与密钥值双载荷时按受众拆分两条（条款升版→订阅者与待审批申请人；凭据更新→全体负责人），双载荷合并问题随之消解。

## User Scenarios & Testing

### User Story 1 — 订阅域通知（申请人与审批人视角） (Priority: P1)

订阅申请提交后当前待办的全部审批人收到通知；审批结果产生后申请人收到通知；订阅被 Owner 取消时被取消方收到附理由的通知；资产下架时待审批申请人收到合并通知（下架 + 申请已取消，不双发）。

**Why this priority**: 订阅审批是平台最高频的协作流程，申请人与审批人的等待感知完全由通知承载。

**Independent Test**: 走完一单订阅全流程（提交→审批→取消），并对一个有待审批申请的资产执行下架，验证四类事件的受众、附件（理由/取消告知）与不双发。

**Acceptance Scenarios**:

1. **Given** 用户提交订阅申请, **When** 申请创建成功, **Then** 该申请当前待办的全部审批人收到站内通知。
2. **Given** 审批结果产生（通过或驳回）, **When** 状态落定, **Then** 申请人收到站内通知（驳回含理由）。
3. **Given** Owner 取消他人订阅（必填理由）, **When** 取消生效, **Then** 被取消方收到附理由的站内通知。
4. **Given** 资产被下架且存在待审批申请, **When** 下架生效, **Then** 待审批申请人收到的下架通知中一并告知其申请已随之取消——合并为一条，不因同一事件收到两条通知。

### User Story 2 — 资产生命周期通知（订阅者视角） (Priority: P1)

订阅者在资产发布新版本（强治理申报附影响说明与迁移指引，未申报为轻量通知）、使用条款升版（附新版条款，不要求重签）、资产被下架（附原因）时收到通知；重新上架不单独发送通知，由发布流程的资产发布通知覆盖（受众为下架时刻的存量订阅者与待审批申请人）；资产删除不触发任何通知。

**Why this priority**: 版本替换与下架直接改变订阅者的集成行为与可用性，是「订阅者知情」承诺的核心承载。

**Independent Test**: 分别触发申报/未申报的版本发布、条款轻发布、下架、重新上架（含从已下架完成）与删除，验证受众、附件与「不双发/不单独发」口径。

**Acceptance Scenarios**:

1. **Given** 资产版本发布完成, **When** 版本替换生效, **Then** 同一时刻通知全部订阅者：申报为强治理变更的附影响说明与迁移指引，未申报的发轻量通知。
2. **Given** 使用条款经轻发布升版, **When** 生效, **Then** 通知全部存量订阅者与该资产的待审批申请人（附新版条款），不要求重新确认。
3. **Given** 资产被下架, **When** 生效, **Then** 全部已通过订阅者收到附下架原因的通知。
4. **Given** 资产从「已下架」完成重新上架, **When** 发布完成, **Then** 不单独发送「资产重新上架」通知——由资产发布通知覆盖，受众为下架时刻的存量订阅者与待审批申请人。
5. **Given** 资产被删除（软删除终态）, **When** 生效, **Then** 不向任何用户发送通知（spec 004 FR-044：下架通知已覆盖订阅者、未发布三态无订阅者、已下架删除时订阅早已清空）。
6. **Given** 资产级服务凭据密钥值经轻发布轮换, **When** 生效, **Then** 通知该资产全体负责人（Owner/Deputy），通知仅含变更事实（「资产服务凭据已更新」）、不包含密钥值本身；**不通知订阅者**（密钥值是平台与资产的契约，非订阅者与资产的契约——2026-08-23 用户裁定收窄）。

### User Story 3 — 负责人治理与任务结果通知（Owner/Deputy 视角） (Priority: P1)

资产全体负责人在以下时刻收到通知：发布准入测评完成、发布任务失败（附失败阶段与原因）、Health Check 连续失败（含失败起始时间与连续失败次数）、出站调用被平台停用或恢复（停用附必填原因）；孤儿资产补员通知新指定的 Owner，原负责人恢复解除孤儿标记时通知全体有效负责人；中止发布通知发起该次发布的 Owner/Deputy。

**Why this priority**: 负责人侧的治理与任务结果通知决定资产的可运营性——负责人不知测评结果、服务不可达或被停用，资产就会失联失管。

**Independent Test**: 逐类触发测评完成、门控失败的发布、HC 连续失败阈值、出站停用/恢复、孤儿补员与恢复、中止发布，验证受众与附件口径。

**Acceptance Scenarios**:

1. **Given** 发布准入测评执行完毕（通过或未通过）, **When** 结果回写, **Then** 通知资产全体负责人。
2. **Given** 发布任务失败（门控未全部通过，或测评未通过且阻断开关开启；含 MCP 门控失败）, **When** 任务结束, **Then** 通知资产全体负责人，附失败阶段与原因摘要（spec 004 FR-042）。
3. **Given** 资产 Health Check 达到连续失败阈值（连续 3 次）, **When** 触发, **Then** 通知资产全体负责人一次（含失败起始时间与连续失败次数）；该失败链持续恶化不再重复通知，探测成功一次后重置；已下架资产不触发（spec 004 FR-029）。
4. **Given** 平台管理员停用或恢复某资产的出站调用, **When** 生效, **Then** 通知该资产全体负责人；停用附必填原因。
5. **Given** 孤儿资产被补员, **When** 完成, **Then** 通知新指定的 Owner；原负责人账号恢复导致孤儿标记解除时，通知该资产全体有效负责人。
6. **Given** 任一 Owner 或 Deputy 中止发布, **When** 中止生效, **Then** 通知发起该次发布的 Owner/Deputy（修订保留）（PRD §9.1/M2-13——该事件未列入 M9-1 十二类清单，本重写补全）。

### User Story 4 — 凭据安全事件通知（凭据持有人视角） (Priority: P2)

个人模型凭据真实调用发生鉴权/权限类失败、本次调用改用平台默认凭据时，通知凭据持有人（附模型名与「请前往 Nexus 申请该模型的权限或更新凭据」引导）；瞬时故障不触发。

**Why this priority**: 这是凭据主体的自我感知通道，频率低但安全归因价值高；依赖凭据解析（spec 007）先行。

**Independent Test**: 构造鉴权类失败与瞬时故障两种场景，验证前者触发通知（含模型名与引导文案）、后者不触发。

**Acceptance Scenarios**:

1. **Given** 个人模型凭据真实调用发生鉴权/权限类失败且本次调用已回落平台默认凭据, **When** 失败发生, **Then** 通知凭据持有人，附模型名与「请前往 Nexus 申请该模型的权限或更新凭据」引导文案。
2. **Given** 个人模型凭据调用发生瞬时故障（非鉴权类）, **When** 发生, **Then** 不触发通知、不改写可用性快照（spec 007 / `docs/adr/0016`）。

### User Story 5 — 通知基础设施（全员视角） (Priority: P2)

顶栏铃铛未读角标 + 通知列表；通知保留 90 天（自产生时刻起算）；列表分页展示（默认每页 20 条）；打开即置为已读；不提供分类筛选、跨模块深度跳转与通知偏好（P1 通知中心承载）；P0 不出现通知中心一级导航入口。

**Why this priority**: 基础设施是全部事件的承载面，但其形态在 P0 刻意轻量；列在末位是因为无业务语义增量。

**Independent Test**: 构造跨 90 天边界的通知与多页列表，验证留存、分页、打开即读与角标未读数。

**Acceptance Scenarios**:

1. **Given** 用户收到通知, **When** 查看顶栏, **Then** 铃铛展示未读角标；打开通知列表分页展示（默认每页 20 条）。
2. **Given** 一条通知, **When** 用户打开该条, **Then** 该条置为已读，角标未读数同步减少（逐条已读）；通知列表另提供「全部设为已读」按钮，点击后当前全部通知置为已读、角标清零。
3. **Given** 通知产生超过 90 天, **When** 查看列表, **Then** 不再展示（自产生时刻起算）。
4. **Given** P0 界面, **When** 查看导航与列表, **Then** 无通知中心一级入口、无分类筛选、无跨模块深度跳转、无通知偏好设置（均为 P1）。

### Edge Cases

- 同一资产短时间连续下架/重新上架多次？——每次下架与发布均按各自事件单独通知；不去重不合并，逐条产生（2026-08-23 用户裁定）。
- Health Check 连续失败持续恶化？——失败链抑制：达阈值（连续 3 次）通知一次后该失败链不再重复通知；探测成功一次即重置，新失败链重新计（FR-026，2026-08-23 用户裁定）。
- 通知受众账号被 Alice 停用？——通知留存但不产生触达；其相关授权已随主体侧失效规则失效（PRD §9.2/§9.3）。
- 下架与出站停用同时成立？——两类通知分别发出（受众与原因不同），调用方提示以下架文案优先（两类文案可同时成立，PRD M1-18）。
- 轻发布同时含使用条款与密钥值两个载荷？——合并为一条轻发布通知（两个附件段），还是两条分别通知——待裁定（见 Open Questions，随 #54 一并）。
- 通知产生时刻资产正处发布进行中？——通知按事件事实正常发出，不受发布互斥影响（互斥约束的是资产操作，不是通知）。

## Requirements

### Functional Requirements

**通知基础设施**

- **FR-001**: 系统 MUST 提供顶栏铃铛未读角标 + 通知列表作为 P0 通知入口；P0 MUST NOT 出现通知中心一级导航入口（原 AC-1；PRD M9-1、§5.1）。
- **FR-002**: 通知 MUST 保留 90 天（自产生时刻起算）；列表 MUST 分页展示（默认每页 20 条，PRD §9.10 列表基线）；已读语义为**逐条已读**——打开单条通知才将该条置为已读，角标未读数等于真实未读条数；同时 MUST 提供「全部设为已读」按钮（原 AC-1；PRD §9.8；逐条已读与按钮为 2026-08-23 用户裁定）。
- **FR-003**: P0 MUST NOT 提供分类筛选、批量已读、跨模块深度跳转与通知偏好设置（P1 通知中心承载）（原 AC-2；PRD M9-1/M9-2、§12.2）。

**订阅域事件**

- **FR-010**: 订阅申请已提交 MUST 通知该申请当前待办的全部审批人（原 AC-3；PRD M9-1）。
- **FR-011**: 订阅审批结果（通过或驳回）MUST 通知申请人（原 AC-4；PRD M9-1）。
- **FR-012**: 订阅被 Owner 取消 MUST 通知被取消方并附理由（Owner 取消必填理由，定义处见 spec 002 / PRD §9.2）（原 AC-7/AC-16；PRD M9-1）。

**资产生命周期事件**

- **FR-020**: 资产发布新版本 MUST 在版本上架替换的同一时刻通知全部订阅者：申报为强治理变更的附影响说明与迁移指引，未申报的为轻量通知；从「已下架」完成的重新上架 MUST 通知下架时刻的存量订阅者与待审批申请人；MUST NOT 单独发送「资产重新上架」通知（原 AC-8；PRD M9-1、§9.1.1；触发语义见 spec 004 FR-021/022/034）。
- **FR-021**: 使用条款升版（轻发布生效时）MUST 通知全部存量订阅者与该资产的待审批申请人，附新版条款，不要求重签（原 AC-9；PRD M9-1、§9.1.1；触发语义见 spec 004 FR-018）。
- **FR-022**: 资产被下架 MUST 通知全部已通过订阅者并附下架原因；该资产的待审批申请人收到的下架通知中 MUST 一并告知其订阅申请已随之取消——合并为一条，不双发（原 AC-10/AC-15；PRD M9-1、§9.1、§9.2；触发语义见 spec 004 FR-028）。
- **FR-023**: 资产删除 MUST NOT 触发任何通知（spec 004 FR-044，2026-08-23 终审裁定；与 M9-1 十二类无「资产被删除」一致）。
- **FR-024**: 孤儿资产补员 MUST 通知新指定的 Owner；原负责人账号恢复导致孤儿标记解除时 MUST 通知该资产全体有效负责人（原 AC-11；PRD M9-1、§9.1.2）。
- **FR-025**: 出站调用停用与恢复 MUST 通知该资产全体负责人，停用附必填原因（原 AC-12/AC-17；PRD M9-1、M8-1；触发语义见 spec 008）。
- **FR-026**: Health Check 连续失败（达阈值，连续 3 次，PRD §9.10）MUST 通知资产全体负责人，含失败起始时间与连续失败次数；抑制策略为**失败链抑制**——达阈值通知一次后该连续失败链 MUST NOT 再重复通知，探测成功一次即重置、新失败链重新计；已下架资产 MUST NOT 触发（spec 004 FR-029，2026-08-23 裁定）。抑制仅作用于通知通道，卡片「当前不可达」标记与详情页「运行状态」字段为常显面、不受影响（原 AC-13；PRD M9-1、M2-4/M2-5；抑制口径为 2026-08-23 用户裁定）。

**任务与凭据域事件**

- **FR-030**: 发布准入测评完成 MUST 通知资产全体负责人（原 AC-5；PRD M9-1；触发语义见 spec 004 FR-008）。
- **FR-031**: 知识库构建完成或失败 MUST 通知触发者与知识库 Owner（原 AC-6；PRD M9-1、§9.6；触发语义见 spec 005）。
- **FR-032**: 个人模型凭据调用失败已回落平台默认凭据 MUST 通知凭据持有人，附模型名与「请前往 Nexus 申请该模型的权限或更新凭据」引导文案；仅鉴权/权限类失败触发，瞬时故障 MUST NOT 触发（原 AC-14；PRD M9-1、§9.3、`docs/adr/0016`；触发语义见 spec 007）。
- **FR-033**: 三条 2026-08-23 裁定连带事件合并为一类「**资产治理通知（负责人）**」（M9-1 十二类 → 十三类），受众统一为负责人侧，按载荷区分（2026-08-23 用户裁定，#54 关闭）：**中止发布**——通知发起该次发布的 Owner/Deputy，载荷为修订保留事实（PRD §9.1、M2-13——该事件未列入 M9-1 原十二类清单，属本重写补全）；**资产服务凭据更新**——密钥值经轻发布轮换时通知该资产全体负责人，载荷仅含变更事实（「资产服务凭据已更新」）、MUST NOT 包含密钥值本身、MUST NOT 通知订阅者（密钥值是平台与资产的契约，非订阅者与资产的契约——受众收窄为 2026-08-23 用户裁定，修正 spec 004 FR-018 原口径）；**发布失败**——发布任务失败（质量门控未全部通过，或准入测评未通过且阻断开关开启；含 MCP 门控失败）时通知资产全体负责人，载荷为失败阶段与原因摘要（spec 004 FR-042）。
- **FR-034**: 轻发布同时含使用条款与密钥值双载荷时，MUST 按受众拆分两条通知：条款升版通知存量订阅者与待审批申请人（FR-021），凭据更新通知全体负责人（FR-033）（2026-08-23 用户裁定）。
- **FR-035**: （保留编号占位——原「发布失败」条目已并入 FR-033 的「资产治理通知（负责人）」类。）

### Key Entities

- **通知（Notification）**: 一条站内通知。关键属性：事件类型、受众（按事件规则计算）、标题与正文（含事件附件：原因/新版条款/影响说明与迁移指引/失败阶段与原因等）、产生时刻（90 天留存起算点）、已读标记（打开即读）。
- **事件类型（Event Type）**: P0 十三类事件——M9-1 原十二类 + 新增「资产治理通知（负责人）」（含中止发布/凭据更新/发布失败三种载荷，受众统一为负责人侧，2026-08-23 用户裁定）。每类事件的受众与附件口径唯一确定。
- **未读角标（Unread Badge）**: 顶栏铃铛上的未读计数，随通知产生增加、打开通知减少。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 十三类事件的受众与附件 100% 符合 FR-010~FR-034 口径（重点：条款升版含待审批申请人、下架申请人合并单条、出站停用附必填原因、HC 失败含起始时间与次数、凭据回落仅鉴权类触发、资产治理通知仅达负责人侧）。
- **SC-002**: 同一下架事件对待审批申请人 100% 只产生 1 条合并通知（不双发）。
- **SC-003**: 重新上架 100% 不单独发送「资产重新上架」通知；资产删除 0 次触发通知。
- **SC-004**: 通知打开 100% 即置为已读且角标同步；超过 90 天的通知 100% 不再展示。
- **SC-005**: 密钥值轮换通知 100% 仅含变更事实、0 次包含密钥值本身。
- **SC-006**: 发布任务失败（含门控失败与 MCP 发布失败）100% 通知全体负责人并附失败阶段与原因。
- **SC-007**: 已下架资产 0 次触发 Health Check 连续失败通知。
- **SC-008**: P0 界面 0 次出现分类筛选/跨模块深跳/通知偏好/通知中心一级入口。

## Assumptions

- 通知事件定义以本 spec 为唯一出处；各源 spec（002/004/005/007/008）只定义触发点语义，不重复定义受众与附件口径。
- 通知的投递通道 P0 仅站内（顶栏角标 + 列表）；邮件/企业微信等外部通道不在 P0（PRD §12.1 仅列轻量站内通知）。
- 通知服务由 mgmt-service 承载（architecture/service-map.md）；事件驱动（hub ADR-001 事件总线），契约影响随 plan 阶段评估（`notification.asyncapi.yaml`）。
- 长耗时任务（测评、构建、发布）的通知时机为任务结果落定时刻；发布中任务的通知不受发布互斥约束。

## Non-Goals / Boundaries

- **通知中心完整版**（P1）：分类筛选、批量已读、跨模块跳转、通知偏好设置（PRD M9-2、§12.2）。
- **邮件/企业微信等外部通知通道**：P0 不承接。
- **通知模板自定义**：P0 事件文案随平台定义，不开放模板编辑。
- **事件触发语义**：各源 spec 的职责（002 订阅状态机、004 发布链路、005 构建管线、007 凭据解析、008 治理动作），本 spec 不重复定义。
- **通知去重**：不做（2026-08-23 用户裁定——逐条产生，事件忠实）；**高频抑制策略**：见 FR-026 的连续失败链口径。
