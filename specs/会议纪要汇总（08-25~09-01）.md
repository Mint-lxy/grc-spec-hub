### 会议一：知识库接口与资产鉴权方案

**主题：Dify 对接、交付时间排期、静态凭据鉴权、护栏策略**

#### 关键讨论

1. **9 月 14 日测试时间确认**
   - 客户（Dify 侧）希望 9 月 14 日来系统上测试，需在 Dify 中搭建的 knowledge base 能直接连上本平台。
   - 客户不会直接在平台上 chat，而是通过接口在 Dify 里调用知识库，**只需要连通腾讯 retrieval 接口即可**，不需要做完整的集成、跳转、角色联动。
   - 时间预期：RO release 本周完成，建 subscription 等约需 3 天，预计下周三拿到资源；理想情况下 9 号完成部署。
   - 待办：与 Dify 厂商要外部知识库接口文档（接口格式是否标准，社区版/企业版差异待确认）。

2. **资产静态凭据鉴权方案**
   - 现状理解：资产方（provider）不提供凭据，由订阅用户在个人密钥库配置静态凭据后，才能调用资产（Agent/MCP）。
   - 关键点：
     - 静态凭据的获取发生在平台之外（用户需自行向资产 owner 获取），平台只负责提示获取方式（资产简介 / Terms of Use 中说明）。
     - 平台 PAT 只校验平台侧身份，出站调用使用用户配置的凭据。
     - 用户旅程存在"割裂"问题——需先在外面订阅、再回平台配置，但这是静态凭据模式的固有形态。
     - 动态鉴权（SCIM / STS / OAuth）需要 provider 额外开发，成本高；现有大部分 provider（包括自家）都只有 SSO + 页面认证，需要改造。
     - 预置大 token 方案（中间商模式）存在"中间人攻击"风险，provider 无法校验用户身份，被否决。
   - **结论**：本期按静态凭据方式落地；找 2~3 个 showcase 体现功能（FIE 侧 agent 可配合改造、security 团队一个小伙子可能有安全类资产可上），越多越好。

3. **护栏（Guardrail）策略**
   - 安全团队周四左右给出护栏要求（会有一份文档），拿到后更新相关 spec（006 等），并让张浩评审工作量和影响。
   - 护栏放在 9 月份排期，不在 8 月。
   - 护栏实现位置：策略数据在 MGM 维护，真正拦截在网关层执行，无独立 guardrail 服务。

4. **Spec 评审**
   - F2001 订阅审批人列等细节：订阅配置（自定义表单步骤）应关联订阅审批人，需细化描述。
   - 张浩正在逐个 spec 审查问题（F29 等），会统排出 plan 和 task 作为验收基线；开发已先行启动。

### 会议二：智能体对话中间过程呈现与系统设计

**主题：对话中间过程呈现、模型适配、多模态、对话渲染、重建机制**

#### 关键讨论

1. **BA 协作方式（Git 分支规范）**
   - BA 在专用分支（spec think PRD v1.2）上工作，spec 讨论成熟后再 merge 回 main；讨论中的 spec 可推远程并告知分支名，不必合入 main。

2. **对话中间过程呈现（体验优化）**
   - 阶段状态流逐步点亮；滚动展示已检索到的文档名并自动收起；思考过程用折叠块展示（问题理解 → 检索 → 重排序 → 过程生成）。
   - 目前有"停止"但没有"继续生成"，待补充。
   - 流式/非流式：
     - 外部 agent 非流式时**不做假流式**，直接整体输出，让用户感知其非流式特性。
     - 流式与非流式命中护栏时行为一致：整段内容撤回，替换为"命中护栏"的用户提醒（避免暴露一半答案）。
   - 中间过程（工具链调用、证据链/佐证文档 traceability）尽量呈现，提升用户等待时的信心与信任。

3. **模型适配器**
   - 平台有"适配器"概念，不同模型供应商需开发不同适配算子（千问 3.7/3.6 一个适配器即可，方舟/百炼/OpenAI 各自需要）。
   - **本期确定接入：方舟、百炼、OpenAI 三家**（Gemini 因合规要求暂缓）。方舟权限由田静申请。

4. **多模态支持**
   - 临时对话暂不支持多模态（模型适配器未涉及）。
   - 知识库文档解析使用 docker / MinerU 自带 OCR 能力（本地小模型，GPU 服务器部署），与 chat 的多模态是两条独立技术线（工程化批量 vs 及时响应通用）。
   - chat 多模态支持排期到 10 月份实现（认为有必要）。
   - 普通文字模型"加眼睛"方案（小模型先解析图片再喂大模型）效果一般，需详细设计。

5. **对话渲染能力**
   - 流式输出避免"哗哗闪动"（前端降低刷新频率即可解决）。
   - 表格：Markdown 表格组件渲染，支持左右滑动，可整块复制（导出 Excel 不做，无沙箱）。
   - 代码块：高亮、行号、一键复制按钮。
   - 流程图：Mermaid 语法（Markdown 扩展插件）。
   - 长答案：分段、折叠、分批展示策略，避免滚屏失控。
   - 倩倩会后整理需要的渲染项清单给开发。

6. **敏感信息脱敏**
   - 员工信息（姓名、身份证号、微信号）展示可接受，但**客户信息严禁明文展示**。
   - 与护栏"整段撤回"机制存在冲突，需向 Copilot 团队求证方案，暂缓决定。

7. **参数修改与全库重建**
   - 触发重建的只有"任务构建参数"（parser/chunk/enhancer），检索类参数（rerank/topK）不触发、即时生效，重建按钮置灰。
   - 库级默认配置与文档级配置（pipeline 复写）两套体系；改库级配置可选择"仅影响后续上传"或"全库重建"。
   - **全库重建必须谨慎**：会覆盖文档级调优过的配置，提供"多选文档重建"的替代方案。
   - 向量模型与向量库绑定不可改。

### 会议三：PRD 智能生成流程

**主题：PRD Generator skill 演示准备**

#### 关键讨论

1. **PRD 智能生成流程**
   - 两个关键 Gate：**Q&A Gate**（AI 基于提供的信息追问 1 轮、约 10~15 个问题澄清需求）→ **Design Gate**（用信息生成可交互原型/HTML，让需求更直观）→ 产出完整 PRD →（必要时）架构拆解（ASIB，将 PRD 拆分为开发任务）。
   - 定位：**PRD 不是 deliverable，而是一个 process**——是 BA 思考、理解客户需求并转化为双方可理解媒介的过程。
   - 人机分工：人把控目标、设定数据边界、最终 sign off；AI 做长文本证据审查、智能拆解开发任务/User Story、检查完整性与一致性，减少人工在格式重写、文字校对上的工作。

2. **PRD Generator 的卖点**
   - 可一键安装到任何项目，基于项目已有知识库/项目背景（行业、WBS、报价等）快速嵌入，问出合适的问题、产出完整可经推敲的 PRD。
   - 演示要求：用 Kero 展示（而非其它工具）、英文演示（金辉酒业项目先转英文 copy）、现场 live demo、先解压展示 skill 详情。

#### 行动项
- [ ] 更新演示材料：突出"PRD 是 process"定位、可一键安装到任意项目的卖点
- [ ] 准备 live demo（英文、Kero 展示、清灰项目案例）

   - 创建者默认拥有目录权限与 KB 创建权限，并可把自己从审批人中删除（待与张浩确认 Alice 侧可行性）。

2. **角色与权限关系**
   - **创建者即 owner**；owner 权限包含 contributor 和 consumer（三个角色独立但 scope 包含：owner ⊇ contributor ⊇ consumer）。
   - 审批人（approver）被指定时，平台自动为其调用 Alice 接口赋予对应角色（避免其再去 Alice 单独申请）。
   - deputy 语义：knowledge 侧 deputy 为"角色审批人 deputy"（仅审批，不自动获得 owner 权限）；与 Marketplace 侧 asset deputy 区分（后续统一命名：Approver Deputy / Asset Deputy）。

3. **目录规则**
   - 含知识库的目录**不允许再创建子目录**（保持层级干净，知识库只存在于叶子目录）；如确有需要，走迁移流程（待确认）。
   - 目录位置一经创建不可移动（如遇零星需求，由运维在后台数据库处理，需出运维 SOP）。
   - 目录排序默认按字母序。

4. **权限申请入口（体验优化）**
   - 查看权限按钮放知识库详情页**右上角固定位置**；左侧导航、目录行内也可增加入口（多点位、醒目、不做太深），并附角色介绍说明（三个角色各自权限）。
   - 无权限用户：隐藏 documents 页签，默认展示 information（含描述、owner、角色申请指引）；有权限用户默认进 documents。
   - IC 等级先不展示（用 public / private 粗粒度控制），等 security 主动找再对齐 T 盘 IC 需求。
   - build stage status 模块与顶部 KPI 重复且易混淆，**删除**，改为在 information 中做静态"构建四步（parser→chunk→enhancer→embedding）"科普介绍。

5. **知识库创建流程（六步）**
   - 位置 → 基本信息（名称、access：public / private / restricted，措辞中 portal users 改 **platform users**）→ description（**必填**，字数待定，倾向 15 字以上，控制质量）→ tag（必选）→ 权限设置（owner / deputy / contributor / consumer 的审批人，交互为搜索+回车添加、可删除）→ 参数配置（parser/chunk/enhancer，带推荐默认配置，可关掉手动配）。
   - 人员名单来源：以 application 名义向 Alice 申请获取组织用户目录（艾玛确认可行，具体流程问陈老师）。
   - 增加**知识库级默认检索（retrieval）配置**：API/chat 调用未传检索参数时使用；跨库检索走默认策略（需加说明文案）。
   - 参数配置项给用户加 hover 说明（如 docling 适用场景）。
   - settings 页：owner/deputy 禁改（从 Alice 同步），增加 schedule（自动化/调度配置，与各连接器刷新频率合并为统一入口，release 1 不展示）。

6. **文档导入（Add Documents）**
   - 四种方式：upload（拖拽上传）、confluence（首次需配置权限，字段：link、是否递归、是否自动更新）、sharepoint、s3（link 抓取）。
   - 支持批量 config / 单个 config；一键构建分 auto / manual；**批量构建不支持 manual**（无法逐个看内部细节）。
   - 失败展示：按 stage 标记（parser 绿、chunk 红…），点错误消息跳转对应 manual 步骤并展示详细报错、可重试。

7. **前端风格**
   - 首页（overview）可以做得更亮眼/现代（玻璃质感 glass UI 作为候选，但注意性能）；**内部页面以稳重、性能优先**为主。
