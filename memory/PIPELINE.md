# Project Memory 管线（PIPELINE）

记忆是**三态流转**的：AI 负责提炼、人类负责裁决、Git 负责追溯。

## 三态模型

```
   写入入口                     now/（当前态）——注入所有 agent 默认上下文
 ① spec 收尾 task ────►  永远精简：state ≤2 页，服务卡各 ≤1 页
 ② 每周定期 digest ──►
 ③ ADR 合并 ─────────►
                              │ 滚动降温（4 周窗口滑出、决策被替代、spec 完成）
                              ▼
                        digests/（过程态，周粒度）——不默认注入，可按需检索
                              │ 季度压缩
                              ▼
                        archive/（归档态）——只用于考古与审计，永不注入
```

**now 的价值来自它的小。** 每次交互都携带 now，所以必须维持在几千 token 内。
这就是滚动降温规则存在的原因——不是任由它增长，而是主动把旧信息降温。

## 目录与状态

| 目录 | 状态 | 是否注入上下文 | 内容 |
|------|------|----------------|------|
| `now/` | 当前态 | ✅ 默认注入 | state、服务卡、决策摘要、词汇表、观察清单 |
| `digests/` | 过程态 | ❌ 按需检索 | 每周一篇摘要 |
| `archive/` | 归档态 | ❌ 永不注入 | 季度压缩、被替代决策、已完成 spec 索引 |

## 三条铁律

1. **AI 永不直接写入 now 主干** —— 一切修改经 PR，人审合并（宪法第六条）。
2. **每条记忆必须带证据链** —— 事实变化条目附来源 PR 链接，便于审核核对。
3. **自动区块与人工区块物理隔离** —— 管线只覆写 `<!-- 自动区块 -->` 内内容，
   `<!-- 人工区块 -->`（owner 的"特别提醒"）永不被机器触碰。

## 自动区块 / 人工区块标记

服务卡等文件用注释成对标记：

```
<!-- 自动区块：由 memory-digest 管线维护，人工修改会被覆盖 -->
...机器生成...
<!-- /自动区块 -->

<!-- 人工区块：owner 手工维护 -->
...人手写...
<!-- /人工区块 -->
```

## 写入入口

- **① spec 收尾 task（主动记忆）**：每个 spec 的最后一个 task 用 `spec-retro`
  生成 `retro.md`，并对 `now/` 相关文件提修改，随实现 PR 一同人审。
- **② 每周 digest（被动记忆兜底）**：每周一由人在 hub 工作区触发：让任意 agent 执行
  `capabilities/prompts/memory-digest.prompt.md`，采集本周各服务仓库合并记录并提炼，提 PR。
- **③ ADR 合并**：新 ADR 合并时，在 `now/decisions.md` 增补一行摘要。

主动与被动互为兜底：收尾 task 已覆盖的变更，周 digest 只做交叉核对。

## 滚动降温规则（由 digest 执行，人审裁决）

- 服务卡"近期重要变化"只保留最近 **4 周**；滑出的条目进入对应季度
  `archive/digests/`，**是移动不是删除**。
- 决策被替代 → 移入 `archive/decisions-superseded.md` 并注明替代原因。
- spec 完成 → 在 `archive/specs-completed.md` 记一行索引。

## 为什么不用纯自动实时更新

实时更新会让 now 变成 commit log 复读机，失去提炼价值；
周粒度匹配人审节奏（每周 10 分钟可持续）；一周窗口让管线看到"一组相关变更
的整体"。真正需实时的信息（契约变更）已由契约门禁的消费者确认流程即时通知。
