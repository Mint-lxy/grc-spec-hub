# Skill: PRD 变更同步（prd-sync）

当 PRD 升版或首次导入时，本 skill 提供标准化流程将 PRD 内容同步到 `specs/` 目录。

## 适用场景

| 触发 | 做什么 |
|------|--------|
| PRD 首次导入（无 specs） | 按功能模块拆解为独立 feature spec |
| PRD 升版（已有 specs） | 分析差异 → 识别受影响 specs → 生成变更 PR |
| 定期一致性检查 | 比对 specs 与 PRD，列出偏差清单 |

## 步骤

### 模式 A：PRD 升版同步

1. **差异分析**：读取旧版 PRD（`docs/prd/*-v<old>.md`）与新版 PRD（`docs/prd/*-v<new>.md`），
   提取新版的「版本说明」章节，按变更条目归类：
   - 新增功能/用户故事
   - 修改的业务规则/状态机
   - 删除/降级的功能（P0→P1 或移除）
   - 新增/修改的待确认事项

2. **影响映射**：将每条变更映射到受影响的 spec 目录（根据 spec 的 PRD 来源标注）：
   ```
   变更: M1 新增第 13 类通知（模型凭据回落）
   影响: specs/009-notification/spec.md — 需新增 AC 条目
         specs/007-credential/spec.md — 需更新凭据解析规则
   ```

3. **生成变更清单**：输出 markdown 表格：

   | 变更摘要 | 来源章节 | 受影响 spec | 操作（新增AC/修改AC/删除AC/新建spec） |
   |----------|----------|-------------|--------------------------------------|

4. **执行更新**（需人确认后）：
   - 逐个 spec 应用变更，保持 AC 编号连续
   - 更新 spec 头部的 PRD 来源引用（版本号）
   - 新增功能若不属于任何现有 spec → 建议创建新 spec 目录
   - 降级/移除的功能 → 从功能需求移到「非目标/边界」

5. **更新 docs/prd/README.md**：文件清单同步。

### 模式 B：首次拆解

1. 读取 PRD 的 §7 功能清单与 §6 用户旅程。
2. 按功能模块（M1–M10）+ 用户旅程（J1–J8）交叉分组。
3. 每组生成一个 `specs/NNN-<slug>/spec.md`，遵守 `sop/artifacts.md` 格式。
4. 确保每个 AC 条目可追溯到 PRD 章节号。

### 模式 C：一致性检查

1. 遍历 `specs/*/spec.md`，提取所有 AC 条目。
2. 与 PRD 功能清单逐条比对：
   - **spec 有但 PRD 无** → 标记为「spec 超出 PRD 范围」
   - **PRD 有但 spec 无** → 标记为「spec 遗漏」
   - **描述不一致** → 标记为「偏差」并列出双方表述
3. 输出偏差报告。

## 输出格式

每次执行输出：
1. **变更影响分析表**（模式 A）或 **偏差报告**（模式 C）
2. **待执行操作清单**（修改哪些文件、新增/删除哪些 AC）
3. 人确认后执行文件修改

## 铁律

- **不自行发明需求**：spec 内容只能来自 PRD，不可凭常识补充。
- **保持可追溯**：每个 AC 标注 PRD 来源（§章节号 + 功能编号）。
- **变更最小化**：只改受影响的部分，不重写未变更的 AC。
- **人审守门**：变更清单输出后等待人确认，不自动合并。
- **版本类字段标注**：涉及状态机或业务规则变更时，在 spec 的「未决问题」中标注是否需要同步更新 plan.md。

## 完成判据

- 变更分析表覆盖 PRD 版本说明中的全部条目
- 受影响 spec 已更新且 AC 编号连续
- spec 头部 PRD 来源版本号已更新
- docs/prd/README.md 已同步
