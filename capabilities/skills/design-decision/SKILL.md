# Skill: 设计方案抉择（design-decision）

把"拍脑袋选方案"变成有据可查的标准流程。产出是**带出处的推荐 + 权衡表**，
用户确认后落 ADR。

## 角色定位

执行本 skill 时，你是**本项目的首席架构师**，不是问答机器：

- **先懂诉求再答问题**：用户的提问往往是表层症状（"放 A 还是 B？"），
  背后可能是更深的诉求（担心耦合/担心以后难改/担心性能/不清楚职责边界）。
  先推断真实诉求并向用户复述确认，再展开分析。
- **主动带着项目背景思考**：你对项目的了解来自 hub 事实源，不来自记忆。
  每次都以第 2 步查到的现状为准，不臆断。
- **对推荐结果负责**：给出明确立场并陈述代价，把最终决定权交给用户，
  但不把选择难题推回给用户。

## 铁律

1. **事实先行**：先查 hub 事实源（ADR/specs/service-map/contracts），
   再给意见。已有决策约束新决策——与既有 ADR 冲突时必须显式指出。
2. **不许只给一个方案**：至少列出 2–3 个候选，包括"什么都不做/维持现状"
   （如适用）。用户提出的方案必须在候选之列，即使最终不推荐。
3. **推荐必须给理由**：理由必须落到具体判据（数据所有权、职责边界、
   调用链跳数、演进独立性、测试成本），不许用"更优雅""更现代"等模糊词。
4. **YAGNI 检查**：如果某方案的好处依赖"未来可能出现的第三种情况"，
   明确标注为投机性收益，降权处理。
5. **决策不落地不算完**：用户确认后必须走第 6 步（落 ADR + 同步文档），
   只聊不记等于没发生。

## 步骤

### 1. 理解诉求并澄清问题

1. **推断真实诉求**：用户在担心什么？（职责边界不清 / 未来演进受限 /
   性能或调用链 / 与既有决策冲突 / 单纯没把握）。用一句话复述：
   "你的核心诉求是 ___，对吗？"
2. **重述为可决策句式**：**"X 应该放在/采用 A 还是 B，判据是什么？"**
3. 若关键输入缺失（调用方是谁、数据在哪、变更频率、性能预算），
   用结构化提问一次问齐，不要挤牙膏式反复追问。

### 2. 查事实源

按问题类型检索（参照 hub-qa 路由表）：

| 要查什么 | 去哪查 |
|---|---|
| 相关既有决策 | `architecture/adr/`、`memory/now/decisions.md` |
| 服务职责边界 | `architecture/service-map.md`、ADR-001 |
| 数据归属 | 相关服务的 spec / ADR 中的数据所有权表 |
| 接口现状 | `specs/000-platform/api-landscape.md`、`contracts/` |
| 需求约束（AC） | `specs/NNN-*/spec.md` |

输出一小节「现状」：引用相关 AC 编号、ADR 编号、已有端点。

**协同已有 skill 推理**（按需调用，不重复造轮子）：

| 场景 | 借用的 skill |
|---|---|
| 涉及接口形态（分页/幂等/版本化/REST vs gRPC） | `sysdesign-api-design` 等 sysdesign-* 知识库 |
| 需要事实性答疑（谁定义的/为什么这么设计） | `hub-qa` 的路由与出处规范 |
| 方案对比需要图示（时序/组件依赖） | `puml` 生成时序图/组件图辅助评审 |
| 决策落地涉及跨服务契约变更 | 落地阶段转 `contract-change` 流程 |

### 3. 列候选方案

每个候选一句话描述。常见抉择模式与首要判据：

| 抉择模式 | 首要判据 |
|---|---|
| 功能放哪个服务 | **数据所有权**——谁拥有判定所需的数据，逻辑就放谁那里；不拥有数据的服务会变成 pass-through proxy |
| 一个接口还是多个 | 入参/出参/校验逻辑重合度——低于一半就拆；"统一接口"若内部全是 if-else 分派，只是把复杂度搬了个位置 |
| 要不要抽象统一两个相似物 | 域模型差异表——生命周期/创建者/绑定粒度差异大则不合并实体，只统一接口层或策略层 |
| 同步调用还是事件 | 时序耦合与失败语义——需要即时结果用同步；只需最终一致用事件 |
| 选型 A 还是 B（框架/中间件） | 团队栈、运维成本、与既有选型（plan 000）的一致性 |

### 4. 权衡表

固定格式，逐行填实：

```markdown
| 方案 | 优点 | 缺点 | 何时选它 |
|------|------|------|---------|
```

每格必须具体（"多一次网络跳"而非"性能差"；"需反调 mgmt 取数据"而非"耦合高"）。

### 5. 给出推荐，请用户拍板

- 明确说"推荐 X"，不许"两个都行看你喜好"。
- 理由 2–4 条，每条对应第 3 步的判据。
- 指出推荐方案的**代价**和缓解措施（没有免费的方案）。
- 与既有 ADR 的关系：兼容 / 需修订某条 / 需新 ADR。
- **显式请用户拍板**：用结构化提问列出候选方案（标注推荐项），
  让用户明确选择。选项之外允许用户提出修改意见——若用户提出变体，
  回到第 4 步补充该变体的权衡后再次请拍板。

### 6. 确认后落地

用户拍板后（不拍板不动手）：

1. **落 ADR**：按 `architecture/adr/template.md` 新建 `NNN-<slug>.md`，
   备选方案表直接复用第 4 步的权衡表，更新 `architecture/adr/README.md` 索引。
2. **同步受影响文档**：
   - 接口变化 → `specs/000-platform/api-landscape.md`
   - 与既有 ADR 交叉 → 修订对应 ADR 并互相链接
   - 服务依赖变化 → `architecture/service-map.md`
   - 决策摘要 → `memory/now/decisions.md`（如存在）
3. **登记后续项**：产生的待办（如"需在 contracts/ 落正式契约"）
   记入 `memory/now/watchlist.md`（如存在）；
   涉及正式契约变更的，走 `contract-change` skill 的完整流程。

## 完成判据

- 权衡表中每个候选的优缺点均可追溯到具体判据；
- 推荐已被用户明确接受或否决；
- 接受的决策已落 ADR、索引已更新、受影响文档已同步。

## 反模式

- ❌ 只回答字面问题不挖诉求——用户问"放哪"，真正担心的可能是"以后难拆"
- ❌ 跳过第 2 步直接给意见——脱离项目现状的建议是通用废话
- ❌ 权衡表里写"简单""灵活""优雅"——不可验证的形容词
- ❌ 用户说"就这么定了"之后不落 ADR——三个月后没人记得为什么
- ❌ 为对称而对称地硬凑第三个候选——凑数方案浪费评审注意力
