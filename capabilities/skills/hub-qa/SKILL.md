# Skill: Hub 只读问答（hub-qa）

证据优先的项目知识检索与解释。只读、不修改任何仓库文件。

---

## 铁律

1. **只答有出处的**：每个关键结论附 hub 内文件路径（精确到章节标题或行号）。hub 里没有的事实，明说「Hub 未记录」，**不许推测编造**。
2. **以事实层为准**：口头共识、聊天记录、外部常识都不是事实源；与 hub 冲突时以 hub 为准，并指出冲突。
3. **保留不确定标记**：标注 `[待确认]` 的事实，回答时必须保留该标注。
4. **不修改仓库**：不写入任何文件、不更新状态、不登记条目。需要写入时路由到对应 Skill。
5. **不把计划当实现**：Spec 存在 ≠ 功能已上线；task 标记完成 ≠ 代码已部署。区分文档状态与实现证据。
6. **消歧义优先**：同名实体（服务/Feature/术语）不得静默猜测，先从仓库上下文消歧，仍无法确定则向用户确认。

---

## 问题分类

| 类别 | 典型问题 |
|------|----------|
| 项目概览 | 项目解决什么问题、包含哪些领域、有哪些服务、整体架构 |
| 服务与架构 | 某服务职责、服务间交互、拆分依据、能力归属 |
| 需求与规格 | 某领域需求清单、验收条件、定义某功能的 Spec、需求覆盖范围、未澄清问题 |
| 设计决策 | 为什么采用某技术/模式、ADR 内容与状态、决策是否仍有效、约束来源 |
| 契约与依赖 | 某 API/事件的生产方消费方、修改契约影响谁、字段定义位置 |
| 计划与进度 | 项目当前进展、未完成任务、阻塞项、负责人、里程碑 |
| 影响分析 | 修改某组件/决策/需求波及哪些文件和服务（只读分析，不执行变更） |
| 信息定位 | 某约束记录在哪、搜索特定关键词、找到某结论原始出处 |

## 检索流程

### 第一步：理解问题

识别：
- 涉及的实体（服务名、Spec 编号、ADR 编号、术语）
- 问题类别（上表）
- 是否需要跨文件汇总
- 是否涉及当前状态还是历史状态
- 是否存在需消歧的同名概念

### 第二步：定位数据源

**检索路由表**（按问题类型确定首查文件）：

| 问题类型 | 首查位置 |
|---|---|
| 项目元信息（名称/范围/锚点） | `hub.config.yaml` |
| 服务清单/职责/依赖方向 | `architecture/service-map.md`、`architecture/services.manifest.yaml` |
| 需求/验收标准/为什么做这个 feature | `specs/NNN-*/spec.md` |
| 技术方案/涉及哪些服务 | `specs/NNN-*/plan.md` |
| 接口字段/事件 schema/错误码 | `contracts/`、`architecture/cross-cutting/error-codes.md` |
| 为什么这么设计（决策） | `architecture/adr/`、`memory/now/decisions.md` |
| 被取代的决策 | `memory/archive/decisions-superseded.md` |
| 术语定义 | `memory/now/glossary.md` |
| 项目现状/风险/近期变化 | `memory/now/state.md` |
| 待办/阻塞/未决问题 | `memory/now/watchlist.md` |
| 某服务的详细记忆 | `memory/now/services/<svc>.md`，下钻 `memory/digests/` |
| 跨领域规范（认证/错误码/可观测性） | `architecture/cross-cutting/` |
| 流程/审批/门禁 | `sop/README.md`、`gates/GATES.md` |
| 编码/测试/评审标准 | `standards/` |
| 契约政策与变更规则 | `contracts/POLICY.md` |
| PRD/用户旅程 | `docs/prd/`、`docs/user_journey/` |
| 谁登记/谁修改/谁决定（人员溯源） | 条目文本中的责任人标注 + git 提交记录（见「人员溯源」节） |

**搜索策略**：优先按路由表精确定位文件 → 搜索 manifest/registry/索引 → 全文搜索缩小范围 → 读取必要片段。不要为一个局部问题无差别加载整个仓库。

### 第三步：交叉验证

对架构、决策、进度、责任归属和依赖关系等问题，尽量用 ≥2 个来源验证。

检查：
- 文档/ADR 状态（Draft/Proposed/Accepted/Deprecated/Superseded）
- 日期与版本
- Spec 状态（Draft/In-Progress/Reviewed/Done）
- 是否为模板或示例（`templates/`、`_example/`）
- watchlist 中是否有相关未决项
- 是否存在相互冲突的定义

**进度问题额外检查**：
- 区分"计划完成"（Spec 存在）vs"文档标记完成"（状态字段）vs"有实现证据"（服务卡或 Git 记录提及）vs"无法从 Hub 判断"
- task 标记 Done 不代表已部署上线

### 人员溯源（git 提交记录）

当问题涉及**谁发起、谁登记、谁修改、谁决定**（watchlist 条目、ADR、spec 裁定、契约变更等）时，除条目文本中的责任人标注外，MUST 用 git 提交记录补充操作人证据：

**常用命令**（只读，不改仓库）：

```powershell
# 谁引入/修改了包含某关键词的内容（watchlist 条目溯源首选）
git log -S "关键词" --format="%h %ad %an <%ae> %s" --date=short -- <文件路径>

# 某文件的完整变更史（谁在何时改过）
git log --follow --format="%h %ad %an <%ae> %s" --date=short -- <文件路径>

# 某一行当前版本的最后修改人（定位到具体行号后使用）
git blame -L <起始行>,<结束行> --date=short -- <文件路径>

# 查看某次提交的完整改动（验证该提交确实引入了目标内容）
git show <hash> --stat
```

**输出要求**：
- 报告提交人时给出 **name + email + 提交 hash + 日期**，如 `Zhang Hao <zhang.hao@example.com>（cb1c992，2026-08-22）`。
- 拉取 watchlist 时，对用户关心的条目默认附「登记提交」与「最后修改提交」两条溯源（条目多时仅对被点名条目做溯源，不逐条全量跑）。

**语义边界（必须区分三种角色）**：

| 角色 | 来源 | 说明 |
|---|---|---|
| **责任人/决策人** | 条目文本中的标注（如【责任人：Zhang Hao】、用户裁定） | 业务权威，以文本标注为准 |
| **登记人/操作人** | git 提交的 author | 只是把内容写进仓库的人，可能是代登记 |
| **信息来源** | 条目描述中的出处（会议/用户指令/BA 裁定） | 决策发生的场合 |

git 提交人 ≠ 决策人。若文本无责任人标注、仅有 git 记录，回答时明确写「登记人为 X（git 记录），决策人 Hub 未记录」。另注意：本仓库存在共享账号提交（如 Zeng Ziyang 曾用 BA 账号 + 本人 SSH key 提交，见 state.md 2026-08-22 记录），email 与实际操作人可能不一致，发现可疑时交叉核对 state.md/watchlist 中的人名记载。

### 第四步：形成回答

对每个关键结论标记确定性级别：

| 标记 | 含义 |
|------|------|
| **已确认** | 由权威文件直接支持 |
| **综合判断** | 由多份材料推导得出，非单一文件直接陈述 |
| **存在冲突** | 多个有效来源给出不同定义 |
| **Hub 未记录** | 没有找到足够证据 |
| **可能已过期** | 来源存在时效性问题（如 state.md 更新周次过旧） |

## 权威来源优先级

冲突时按以下顺序裁定（基于本仓库的守门点与事实源设计）：

1. 宪法（`.specify/memory/constitution.md`）
2. 当前生效的 Accepted ADR > Proposed ADR > 普通设计说明
3. 已 Reviewed/Done 的 Spec > Draft Spec > README 描述
4. 正式契约（`contracts/`）> 调用示例或描述性文档
5. `services.manifest.yaml` / `service-map.md` 的结构化字段 > 自然语言汇总
6. `memory/now/` > `memory/digests/` > `memory/archive/`
7. 明确标注最新版本的文件 > 已废弃版本
8. 具体领域文档 > 泛化项目概述

**不适用作权威判据**：
- Git 修改时间不能单独判定业务内容权威性
- Git 提交人（author/email）只证明「谁写入仓库」，不证明「谁做的决策」——决策归属以条目文本标注为准
- 任务完成标记不等价于实现已上线
- 模板/示例文件不代表正式决策

## 冲突处理

发现冲突时：
1. 列出冲突的文件和具体内容
2. 说明按优先级更倾向哪个结论
3. 指出 watchlist 中是否已有相关跟踪项
4. 如果无法判断，明确建议项目维护者确认

---

## 来源引用规范

每个关键结论附来源，格式：

```
[path/to/file.md](path/to/file.md) — "章节标题"
```

可附行号：`path/to/file.md:42`（但不可只有行号而缺语义说明）。

多来源结论分别列出主要来源。

**禁止**：
- 编造文件路径或章节名
- 引用未实际读取的文件
- 仅说"根据项目文档"而不给具体出处
- 将模板/示例/草稿作为正式决策引用
- 使用外部常识替代 Hub 中的项目事实

外部知识仅用于解释通用概念，并必须标注：
> 以下是通用解释，不是 Hub 中记录的项目决策。

## 回答格式

根据问题复杂度自适应。

**简单事实问题**：
```
<直接结论>

来源：
- [文件路径](文件路径) — 章节
```

**跨文档分析**：
```
## 结论
<简洁结论>

## 依据
- <证据 1 及来源>
- <证据 2 及来源>

## 不确定性或冲突
<没有则省略本节>
```

**进度问题**：
```
| 工作项 | 文档状态 | 实现证据 | 判断 | 来源 |
|---|---|---|---|---|
```

**影响分析**：
```
| 受影响对象 | 影响原因 | 证据 | 确定性 |
|---|---|---|---|
```

**人员溯源**：
```
| 角色 | 人 | 证据 | 确定性 |
|---|---|---|---|
| 决策人 | <人名或 Hub 未记录> | <条目文本标注 + 文件路径> | 已确认/Hub 未记录 |
| 登记人 | <name <email>> | <hash，日期，文件> | 已确认 |
| 最后修改 | <name <email>> | <hash，日期> | 已确认 |
```

不输出空章节。简单问题不套用复杂模板。

## 只读边界与 Skill 路由

当用户问题包含写入意图时，停止在分析阶段，提供只读结论后推荐对应 Skill：

| 写入意图 | 推荐 Skill |
|----------|------------|
| 把结论写进 ADR / 新建 ADR | `architecture-decision-records` |
| 在方案间做选择并落地 | `design-decision` |
| 修改/新建/重写 Spec | `speckit-specify` |
| 生成实现计划 | `speckit-plan` |
| 修改或新增契约 | `contract-change` |
| 更新项目记忆/同步漂移 | `memory-sync` |
| 管理 watchlist/登记缺口/登记术语 | `hub-assistant` |
| 更新进度/任务状态 | `hub-assistant` |
| 检查工件一致性并修复 | `speckit-analyze`（只读报告）→ 对应写入 Skill |

路由时说明推荐理由，不要仅给 Skill 名。

## 与 hub-assistant 的边界

| 维度 | hub-qa | hub-assistant |
|------|--------|---------------|
| 本质 | 只读问答与信息检索 | Hub 运维写入操作 |
| 产出 | 带出处的回答 | 文件变更（watchlist/glossary/state） |
| 触发词 | 问、查、为什么、哪里、什么、是否 | 新增、更新、关闭、登记、总结 watchlist |
| 修改仓库 | 从不 | 是（守门文件需人审） |
| 缺口处理 | 指出 Hub 未记录，建议用 hub-assistant 登记 | 执行登记操作 |

## 完成判据

- 每个关键结论有出处引用
- 无出处的部分已标注确定性级别
- 冲突已显式列出而非隐藏
- 进度回答区分了文档状态与实现证据
- 人员溯源问题附了 git 证据（name + email + hash + 日期）并区分了决策人与登记人
- 未越过只读边界
- 写入意图已路由到对应 Skill
