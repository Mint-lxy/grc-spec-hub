# 手册三：已上线的系统（生产环境运行中）

> 前提：已完成 [公共准备](README.md)。
> 与手册二（部分开发）的差别：所有服务都是存量，且**生产在跑、不能错**。
> 策略是"**灰度接管**"：不停机、不重构、不大爆炸迁移——hub 先接管**新变更**，
> 存量登记按优先级逐步补齐。

---

## 总路线图

```
第 1 周   绑定项目 + 宪法 + 现状盘点（service-map/manifest 反填）
第 2–3 周 高风险服务优先：契约逆向 + 记忆卡 + link-hub
第 3 周起 新变更一律走 hub（spec + 契约先行从此生效）
持续      低风险服务的登记利用日常变更"顺手补"
```

---

## 第 1 周：绑定与盘点

### 1. 绑定项目

按 [手册一·阶段 0](01-new-system.md#阶段-0把-hub-绑定到你的项目半天)。

### 2. 宪法：加上线系统特有的两条

照常共写六条骨架（见手册一），已上线系统建议额外考虑写入：

- **兼容窗口是硬约束**：破坏性契约变更必须新旧版本并存，旧版本保留期
  `[待确认: 如一个里程碑]`，且需全部消费方在 retro 确认迁移完成才可下线；
- **生产事故回溯入记忆**：每次线上事故的根因与修复必须进 watchlist/服务卡。

### 3. 现状盘点（反填 service-map + manifest）

按 [手册二·1.2/阶段 2](02-partial-system.md#12-架构图--hub-格式)：
架构图转 Mermaid、全部服务进 manifest（milestone 都写 `M0-已上线`）、补记 ADR。
**额外做**：把 [cross-cutting/](../architecture/cross-cutting) 三件按**线上实际情况**填
（现在用什么认证、什么监控、错误体长什么样——写实际的，不写理想的）。

### 4. 初始化记忆（上线系统的记忆最值钱）

- [state.md](../memory/now/state.md)：当前版本、在跑的里程碑、近期计划；
- [watchlist.md](../memory/now/watchlist.md)：**把团队都知道的技术债/坑一次性倒进来**
  （那些"只在老员工脑子里"的信息，这是 hub 对上线系统的最大价值）；
- [glossary.md](../memory/now/glossary.md)：业务黑话逐条定义（防 agent 望文生义）。

## 第 2–3 周：按风险排序接入服务

**排序依据**：① 近期要改动的服务最先；② 被依赖多（入度高）的其次；③ 稳定不动的最后。

对每个服务，执行 [手册二·阶段 3A + 3B](02-partial-system.md#阶段-3a存量服务接入每个约-1-小时不动业务代码)：
搬同级目录 → 补 AGENTS.md 等入口 → link-hub → 契约逆向 → 记忆卡。

**上线系统的契约逆向有一条铁则**：以**线上实际行为**为准——不是代码注释、不是过时的
wiki、更不是"当初设计"。核对手段（按可得性选）：网关/APM 的真实流量 schema、
集成环境抓包、consumer 方的实际调用代码。文档与实际不符的地方是最大的坑，
逐条标 `[待确认]` 并找 owner 确认。

**暂时接不进来的服务**（外包维护、冻结待下线等）：service-map 照常登记
（owner、契约、`职责` 里注明状态），仓库可以不 link-hub。地图必须完整，接线可以缺席。

---

## 第 3 周起：新变更一律走 hub（接管完成的标志）

从某个明确日期起团队约定：

1. **任何新需求**先在 hub `/speckit.specify`，无 spec 不开工（宪法第一条生效）；
2. **任何接口改动**先走 `/contract-change`（宪法第二条生效）——上线系统尤其注意：
   - 破坏性变更一律"新版本并存 + 双写过渡"，禁止原地改；
   - 消费者确认 `confirmed-by:<svc>` 集齐才能合并；
   - 旧版本下线单独开清理 spec，确认全部消费方迁移后执行；
3. 每个 spec 收尾必须更新记忆（宪法第五条生效）。

之后的日常与 [手册一·阶段 4/5](01-new-system.md#阶段-4第一个-feature跑通一圈之后每个需求都这样走) 完全相同。

## 常见问题

- **存量服务太多，登记不完怎么办？** 只有"近期会改的"必须先登记；其余的
  等第一次被某个 spec 涉及时"顺手"补契约和记忆卡（plan 的「涉及服务」章会逼出来）。
- **线上有紧急 hotfix 怎么办？** 宪法第一条已留口子：可先修后补，PR 标
  `hotfix-pending-spec` 并链接后续 spec issue，补 spec 是合并的前置条件。
- **已有 CI/CD 流水线，和 hub 门禁什么关系？** 不冲突。hub 门禁是本地脚本 + 人审，
  你可以把 `gates/scripts/` 挂进现有 CI 当额外关卡（可选增强，见 [gates/GATES.md](../gates/GATES.md)）。
- **多环境（staging/prod）契约不一致？** 契约以 prod 为准登记；差异记 watchlist，
  收敛差异本身立一个 spec。
- **接管前的历史需求文档要迁进 specs/ 吗？** 不迁。specs/ 从接管日起记新需求；
  历史文档如有长期价值，摘要进 ADR 或 glossary，原件留在原处。
